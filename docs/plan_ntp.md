# План: NTP-подобная синхронизация часов

## 1. Цель

Реализовать механизм согласования часов клиента и сервера с целевой точностью ≤ 50 мс. Это базовый слой алгоритма синхронизации видео: без надёжной оценки `offset` и `rtt` поле `execute_at` в командах Play/Pause/Seek работать не будет, а значит не будет и сведения рассинхрона между клиентами в окно ≤ 400 мс.

После этого этапа клиент должен уметь отвечать на вопрос «сколько сейчас на серверных часах в моих локальных миллисекундах» с погрешностью, измеримой и контролируемой.

## 2. Бэкенд

### 2.1 Расширение `backend/app/schemas/messages.py`

Добавить две схемы под секцией «Входящие» и «Исходящие»:

```python
# Входящие
class TimeSyncRequestPayload(BaseModel):
    client_send_ms: float  # клиентское время t0, миллисекунды с дробной частью

class TimeSyncRequestMessage(BaseModel):
    type: Literal["TimeSyncRequest"]
    payload: TimeSyncRequestPayload

# Исходящие
class TimeSyncResponsePayload(BaseModel):
    client_send_ms: float    # эхо t0 — клиент по нему сопоставляет запрос/ответ
    server_receive_ms: float # серверное время t1 (момент приёма запроса)
    server_send_ms: float    # серверное время t2 (момент непосредственно перед отправкой)

class TimeSyncResponseMessage(BaseModel):
    type: Literal["TimeSyncResponse"] = "TimeSyncResponse"
    payload: TimeSyncResponsePayload
```

Все три временные метки — `float` в миллисекундах с дробной частью, чтобы сохранить субмиллисекундную точность через JSON. Использовать `int` нельзя: округление до целых мс на серверной стороне вносит ошибку ±0.5 мс на каждое измерение, что бессмысленно ухудшает точность при том, что JSON прекрасно сериализует float.

### 2.2 Обработка в `backend/app/ws/handler.py`

Внутри `while True` (строки 120–129) расширить разбор:

1. Прочитать `raw`. **Сразу же**, до любого парсинга, зафиксировать `t1_candidate = server_now_ms()`. Это потенциальный t1 для TimeSync. В коде — комментарий, поясняющий: «фиксируем как можно раньше, чтобы не включать в t1 время на JSON-разбор и валидацию Pydantic; используем только если тип сообщения окажется TimeSyncRequest, иначе значение выбрасывается».
2. `parsed = json.loads(raw)`, `msg_type = parsed.get("type")`.
3. На `msg_type == "TimeSyncRequest"`:
   - Распарсить `TimeSyncRequestMessage.model_validate(parsed)`.
   - Сформировать ответ: `server_send_ms = server_now_ms()` фиксируется **в момент непосредственно перед** `websocket.send_text(...)`, не раньше.
   - Отправить `TimeSyncResponseMessage`, передав `t1_candidate` в поле `server_receive_ms`.
   - На ошибку валидации — отправить `Error` с кодом `INVALID_MESSAGE` (но соединение не закрывать; одна кривая TimeSync-метка не должна рушить сессию).
4. Остальные неизвестные типы — оставить текущее предупреждение в логах.

Логирование TimeSync на уровне `DEBUG`, не `INFO`: при 30 клиентах и интервале 5 сек это 6 событий/сек, в `INFO` они засорят журнал и помешают видеть события синхронизации видео.

### 2.3 Источник серверного времени: `time.time()` vs `time.monotonic()`

**Краткий ответ: используем `time.time() * 1000` для всех серверных меток (t1, t2, server_timestamp, execute_at).**

Развёрнутое обоснование (войдёт в главу 2 диплома):

| Свойство | `time.time()` | `time.monotonic()` |
|---|---|---|
| Привязка к Unix-эпохе | да | нет (произвольный baseline) |
| Защищён от прыжков NTP/admin | нет | да |
| Совместим с протокольными метками | да | нет — клиент видит «странные» числа |
| Совместим с базой данных, логами, метриками | да | нет |
| Точность на современных Linux/Windows | мкс | мкс |

Аргументы за `time.time()`:

1. **Согласованность с уже описанным протоколом.** `docs/protocol.md` явно фиксирует `server_timestamp` и `execute_at` как Unix ms (пример `1716890001000`). Переход на monotonic потребует объяснений «почему мы шлём 4815162342 без явного смысла» и сломает совместимость с обычными отладочными утилитами (логами, БД, графиками).

2. **NTP-алгоритм компенсирует прыжки на клиенте, не на сервере.** Симметричное прыгание серверных часов между t1 и t2 (между приёмом и отправкой — обычно сотни микросекунд!) практически невозможно: даже NTP-коррекция дольше. Если случится — резко вырастет RTT, и медианный фильтр с отсечением 25% худших измерений выкинет такую точку.

3. **Сервер в проде синхронизирован NTP/chrony, дрейф ничтожный.** Это типовая инфраструктура; ситуация «server admin вручную сдвинул время на 5 минут во время сессии» нерелевантна для диплома.

Аргументы за `time.monotonic()` (отвергаем):

1. **Защита от прыжков на сервере.** Реально полезно для долгоживущих измерений (часы, дни), а не для пары t1/t2 в пределах одного хэндлера.
2. **Чуть выше монотонность.** На том же порядке, что и `time.time()` на современных ОС.

**Альтернативный гибрид**, который мы НЕ применяем, но упомянем в дипломе для полноты: можно было бы хранить пару `(wall_anchor, monotonic_anchor)`, выставлять её при старте сервера и считать `server_now = wall_anchor + (monotonic_now() - monotonic_anchor)`. Это даёт неубывающие метки даже при прыжке wall-clock. Для масштаба нашей задачи (короткие сессии, типовая инфраструктура) — оверинжиниринг.

**Реализация:** маленькая утилита `app/sync/clock.py`:

```python
import time

def server_now_ms() -> float:
    """Текущее серверное время в миллисекундах Unix-эпохи с дробной частью."""
    return time.time() * 1000
```

Все места, где нужно серверное время, идут через эту функцию — потом легко поменять источник в одной точке.

### 3.3 Чистые функции в `clockMath.ts`

```ts
export interface Measurement {
  t0: number;  // client_send_ms (performance.now() при отправке)
  t1: number;  // server_receive_ms
  t2: number;  // server_send_ms
  t3: number;  // client_receive_ms (performance.now() при приёме)
  offset: number;  // считается при создании
  rtt: number;     // считается при создании
}

export function computeOffsetMs(t0: number, t1: number, t2: number, t3: number): number {
  return ((t1 - t0) + (t2 - t3)) / 2;
}

export function computeRttMs(t0: number, t1: number, t2: number, t3: number): number {
  return (t3 - t0) - (t2 - t1);
}

export function makeMeasurement(t0: number, t1: number, t2: number, t3: number): Measurement {
  return { t0, t1, t2, t3,
           offset: computeOffsetMs(t0, t1, t2, t3),
           rtt:    computeRttMs(t0, t1, t2, t3) };
}

/**
 * Выбирает робастную оценку offset из окна измерений:
 *   1. сортирует по RTT по возрастанию,
 *   2. отбрасывает trimRatio (доля) с самым большим RTT,
 *   3. из оставшихся берёт медиану offset.
 */
export function selectBestOffset(window: Measurement[], trimRatio: number): number {
  if (window.length === 0) return 0;
  const sortedByRtt = [...window].sort((a, b) => a.rtt - b.rtt);
  const keepCount = Math.max(1, Math.ceil(sortedByRtt.length * (1 - trimRatio)));
  const kept = sortedByRtt.slice(0, keepCount);
  const offsets = kept.map(m => m.offset).sort((a, b) => a - b);
  return median(offsets);
}

export function median(sorted: number[]): number {
  const n = sorted.length;
  if (n === 0) return 0;
  if (n % 2 === 1) return sorted[(n - 1) / 2];
  return (sorted[n / 2 - 1] + sorted[n / 2]) / 2;
}
```

### 3.4 Класс `ClockSync`

```ts
type SendFn = (msg: ClientMessage) => void;

interface ClockSyncOptions {
  windowSize?: number;        // по умолчанию 8
  trimRatio?: number;         // по умолчанию 0.25
  warmupCount?: number;       // по умолчанию 5
  warmupIntervalMs?: number;  // по умолчанию 1000
  steadyIntervalMs?: number;  // по умолчанию 5000
}

class ClockSync {
  constructor(send: SendFn, options?: ClockSyncOptions);

  start(): void;                            // запуск опросов, выставляет running=true
  stop(): void;                             // остановка + очистка таймеров, running=false
  reset(): void;                            // жёсткий сброс окна (вызывается на reconnect)
  handleResponse(payload: TimeSyncResponsePayload): void;  // вызывается извне; no-op если !running

  getServerTime(): number;                  // performance.now() + offset
  getOffset(): number;
  getRtt(): number;                         // медиана RTT окна (для расчётов)
  getLastRtt(): number;                     // RTT последнего измерения (для UI — реагирует на скачки)
  getOffsetUncertaintyMs(): number;         // (medianRtt - minRtt) / 2 — верхняя оценка погрешности offset
  getMeasurementCount(): number;            // всего успешных измерений
  isReady(): boolean;                       // true после первого измерения

  on(event: 'updated', cb: () => void): void;
  off(event: 'updated', cb: () => void): void;
}
```

**Сценарий жизни:**

1. `start()` → ставит флаг `running = true`, ставит таймер на ближайший опрос, начинает фазу warmup.
2. На каждый тик: фиксирует `t0 = performance.now()`, шлёт `TimeSyncRequest { client_send_ms: t0 }`. Перепланирует следующий тик в зависимости от фазы (warmup vs steady).
3. На входящий `TimeSyncResponse` через `handleResponse`:
   - **Если `running === false` — немедленный return** (защита от гонок: ответ мог прилететь сразу после `stop()`).
   - Фиксирует `t3 = performance.now()`.
   - Создаёт `Measurement` через `makeMeasurement`.
   - Кладёт в кольцевой буфер длины `windowSize`.
   - Пересчитывает `offset = selectBestOffset(window, trimRatio)`, `rttMedian = median(rtts)`, `uncertainty = (rttMedian - minRtt) / 2`.
   - Эмитит `updated`.
   - Инкрементит `measurementCount`.
4. `stop()` — `running = false`, `clearTimeout`, обнуление таймера.
5. `reset()` — **жёсткий сброс:** очистка окна, обнуление счётчика, перезапуск warmup. Вызывается при `reconnect` через подписку на `WSClient`. После реконнекта сетевые условия могут отличаться, доверять старым измерениям опасно.

**Сопоставление запрос/ответ.** Не нужно вести очередь pending-запросов: сервер эхом возвращает `client_send_ms` в payload, клиент берёт его как t0. Это значит — даже если ответ потерян или пришёл с большой задержкой, мы не путаем измерения. Заодно избавляемся от необходимости таймаутить «зависшие» запросы — следующий тик уйдёт по расписанию независимо.

**Что делать с поздним ответом.** Если ответ пришёл после следующего запроса — он всё равно валидное измерение (его t0 однозначно идентифицирует пару). Просто RTT у него будет больше, и при наличии 8 измерений в окне его, скорее всего, отсечёт `selectBestOffset`. Никакой явной обработки не нужно.

### 3.5 Интеграция с `WSClient`

Подписка снаружи (в `App.tsx` или в фабрике, которая создаёт обе сущности):

```ts
const ws = new WSClient();
const clock = new ClockSync((msg) => ws.send(msg));

ws.on('message:TimeSyncResponse', (payload) => clock.handleResponse(payload));
ws.on('status_change', (status) => {
  if (status === 'connected') clock.start();
  if (status === 'disconnected' || status === 'reconnecting') clock.stop();
});
```

**`ClockSync` не знает про `WSClient`** — только про абстрактный `send` callback. Это:
- упрощает тестирование (можно подсунуть mock),
- разрывает циклическую зависимость,
- даёт переиспользуемость, если когда-то понадобится синхронизировать что-то ещё.

При реконнекте — на новом `status === 'connected'` после `reconnecting`/`disconnected` — вызывается `clock.reset()` перед `start()`. Сетевые условия после реконнекта могут отличаться, старые измерения устаревают.

### 3.7 Индикатор в `App.tsx`

В `RoomPage` (или прямо в шапке) маленький блок:

```
Sync: offset +12.3 мс ±5.2 мс | RTT 47.1 мс | n=12
```

- При `isReady === false` показывать «синхронизация…».
- `offset` со знаком, одним знаком после точки.
- `±X.X мс` — `getOffsetUncertaintyMs()`. Это и метрика для отладки, и сильный аргумент для защиты диплома: «метод даёт измеримую верхнюю оценку погрешности offset».
- `RTT` — `getLastRtt()` (а не медиана): для UI важна реакция на скачки. Медиана используется в логике (через `getRtt()`) для расчёта `uncertainty`.
- Цветовая индикация (опционально): RTT < 50 мс — зелёный, < 150 мс — жёлтый, иначе красный. Это будет наглядно при демонстрации комиссии.

### 4.1 Добавить vitest

### 4.2 Тесты в `clockMath.test.ts`

Покрытие — **только чистая математика**, никакого мокирования таймеров и сети:

1. **`computeOffsetMs` / `computeRttMs` на синтетических данных.**
   - Случай «идеальная сеть, симметричная задержка»: t0=0, t1=100, t2=101, t3=200 → offset = ((100-0)+(101-200))/2 = 0.5, rtt = 200-0 - (101-100) = 199.
   - Случай «офсет +500 мс, симметричная RTT 100 мс»: t0=0, t1=550, t2=550, t3=100 → offset = ((550-0)+(550-100))/2 = 500, rtt = (100-0)-(550-550) = 100.
   - Случай «асимметричная задержка»: проверить, что формула даёт ожидаемое значение (классический недостаток NTP — асимметрия искажает offset на половину разности задержек).

2. **`median` на чётном и нечётном количестве, на пустом массиве.**
   - `[1,2,3]` → 2.
   - `[1,2,3,4]` → 2.5.
   - `[5]` → 5.
   - `[]` → 0 (по соглашению).
   - Отрицательные значения, дубликаты.

3. **`selectBestOffset` — отсечение выбросов.**
   - 8 измерений, у 2 из них RTT в 10× выше остальных, причём offset у этих двух «загрязнён» (например, +500 мс при истинном offset ≈ 0). Проверить: `selectBestOffset(window, 0.25)` возвращает значение, близкое к 0, а не подтянутое выбросами.
   - Граничный случай: окно из 1 элемента → возвращает его offset.
   - Граничный случай: окно из 4 элементов, trimRatio=0.25 → keepCount=3, медиана из 3.

4. **`selectBestOffset` — медиана работает после отсечения.**
   - Окно с известными offset и RTT, посчитать вручную ожидаемый результат, сравнить.

5. **Стабильность сортировки.** Если у нескольких измерений одинаковый RTT, поведение должно быть детерминированным (не критично, но проверить, что не падает).

6. **Stability under long run.** Генерируется 1000 синтетических измерений: истинный offset = 100 мс + гауссов шум `N(0, 5)` мс на каждое измерение; в 10% случаев — выброс с RTT в 5–10× выше нормы и «загрязнённым» offset (например, +500 или –500). После каждого добавления в окно длины 8 проверяется, что `selectBestOffset` выдаёт значение в диапазоне `[85, 115]` мс. Тест ловит накопительные эффекты, которые не видны на тестах из 8 точек: длительный jitter, периодические всплески, корреляции выбросов. Использовать seedable PRNG (например, `mulberry32`) — тест должен быть детерминированным.

### 4.3 Что НЕ тестируем

Сетевую часть, таймеры, интеграцию с WSClient — нет. Это интеграционные сценарии, они в отдельный заход (вместе с end-to-end тестами WebSocket — следующий этап после команд Play/Pause/Seek).

Тестировать `setTimeout`-логику warmup/steady через fake timers — можно, но трудоёмко и хрупко. Лучше визуально проверить в браузере через индикатор: warmup даёт 5 измерений за ~5 сек, потом частота падает.

## 5. Обоснование ключевых параметров (для главы 2 диплома)

### 5.1 Размер окна `N = 8`

- При **N < 5** медиана нестабильна — одно случайное плохое измерение значительно сдвигает оценку.
- При **N > 12** окно становится инертным: при изменении сетевых условий (например, переход с Wi-Fi на 4G) истинный offset «уплывает» вместе со средним RTT, а медиана продолжает выдавать устаревшее значение десятки секунд.
- **N = 8** при интервале опроса 5 сек покрывает 40-секундное окно. Это достаточно для усреднения jitter и достаточно мало, чтобы за разумное время отреагировать на смену сетевого пути. После отсечения 25% (2 точки) для медианы остаётся 6 значений — комфортный размер выборки.

### 5.2 Отсечение `trimRatio = 0.25`

- Отсекаем **только верх по RTT, не низ.** Это принципиальное отличие от симметричного trimmed mean. В NTP-алгоритме измерения с маленьким RTT — самые точные: ошибка offset ограничена величиной `± (rtt - rtt_min) / 2` (предположение симметричности задержки). Маленький RTT означает, что обе ноги пакета прошли быстро, и асимметрия физически ограничена. Отсекать их — выбрасывать самое ценное.
- **25%** — компромисс: 1/8 (12.5%) слишком мало (при двух одновременных выбросах оба попадают в выборку); 50% — слишком агрессивно, теряем половину данных. 25% надёжно убирает 1–2 типичных всплеска в окне из 8.
- Альтернативу — фильтрацию по абсолютному порогу RTT (например, отбрасывать всё > 500 мс) — не применяем, потому что у разных пользователей нормальный RTT разный (от 5 мс по локальной сети до 200 мс через VPN), фиксированный порог не универсален.

### 5.3 Медиана, а не среднее

- Среднее чувствительно к выбросам: одно измерение с offset на +500 мс при остальных около 0 поднимает среднее на 60 мс (при N=8). После trimming остаются 6 — всё равно одно остаточное искажение на +500 даёт сдвиг ≈83 мс. Это превышает целевую погрешность 50 мс.
- Медиана устойчива: до 50% точек должны быть искажены, чтобы медиана была затронута. После отсечения 25% верха по RTT доля «плохих» точек среди оставшихся ещё ниже.
- Цена — небольшая потеря эффективности на «хороших» данных (при гауссовом шуме медиана даёт оценку на ~25% хуже среднего по дисперсии), но это приемлемо в обмен на робастность.

### 5.4 `performance.now()` вместо `Date.now()` на клиенте

- `Date.now()` — wall clock. Подвержен: NTP-коррекции системного времени, ручному переводу часов пользователем, скачкам после выхода из сна/гибернации.
- Если `Date.now()` прыгнет на +30 секунд между t0 и t3 — у нас один испорченный offset, который медиана съест; но это лишний шум.
- `performance.now()` — монотонные миллисекунды от навигации страницы. Гарантировано неубывает, не подвержен системным сдвигам, имеет субмиллисекундное разрешение в современных браузерах (Chrome ограничивает до 100 мкс из-за Spectre, Firefox до 1 мс или 100 мкс в зависимости от cross-origin изоляции — всё равно лучше Date.now).
- Семантика `getServerTime()` остаётся правильной: `offset = serverWallClock - clientPerformanceNow` — это просто константа сдвига, в которой «зашита» разница между моментом загрузки страницы и Unix-эпохой. Клиенту это видеть не обязательно, он просто складывает: `serverTime = performance.now() + offset`. Когда нужно сравнить с серверным `execute_at` (Unix ms) — вычисляем `localExecuteAtPerfNow = execute_at - offset`, ставим `setTimeout(..., localExecuteAtPerfNow - performance.now())`.

### 5.5 Стартовая фаза 5×1 сек, затем 5 сек

- Первое осмысленное значение offset появляется после первого ответа — это нормально, но **окно** из 1 точки даёт нестабильную оценку. Чтобы стабилизировать offset за разумное время:
  - При 5-секундном интервале с самого старта 8 измерений набираются за 40 секунд. Слишком долго: пользователь может за это время нажать Play.
  - При 1-секундном интервале с самого старта набор окна за 8 секунд, но «дёргает» сеть постоянно — лишний трафик.
- Компромисс: первые **5 измерений каждые 1 сек** (5 сек на разогрев, окно частично заполнено), потом — **5 сек** между измерениями (норма поддержки в стабильном состоянии). За 5 секунд можно дать пользователю надёжный offset с ошибкой, ограниченной jitter сети.
- Эти параметры — настраиваемые через `ClockSyncOptions`, чтобы можно было крутить под разные эксперименты в нагрузочном тестировании.

### 5.6 Интервал в steady-state 5 сек

- Часы клиента и сервера дрейфуют медленно (типично ≤ 50 ppm = 50 мкс/сек). За 5 секунд накопится ≤ 0.25 мс — несущественно по сравнению с jitter сети.
- Более частые опросы (1 раз/сек) — лишний трафик: 30 клиентов × 1 запрос/сек × 2 (туда-обратно) = 60 сообщений/сек на сервере только под TimeSync.
- Более редкие (раз в 30 сек) — медленная реакция на изменения RTT (пользователь переключил сеть).
- 5 сек — эмпирически разумный компромисс, использовавшийся в похожих системах (например, синхронизация в Discord-like приложениях).

## 6. Порядок реализации (по коммитам)

Каждый шаг — отдельный коммит, чтобы при сбое в одном не пришлось откатывать остальное.

1. **Backend: схемы + утилита `server_now_ms`**
   - `app/sync/__init__.py`, `app/sync/clock.py` с `server_now_ms()`.
   - Добавление `TimeSyncRequestMessage`, `TimeSyncResponseMessage` в `messages.py`.

2. **Backend: обработка в handler**
   - В `while True` в `handler.py` — ветка на `TimeSyncRequest`.
   - Проверить вручную через `wscat` или DevTools: ответ возвращается.

3. **Frontend: типы протокола**
   - Расширение `types/protocol.ts` (TimeSyncRequest в ClientMessage, TimeSyncResponse в ServerMessage).

4. **Frontend: чистая математика + тесты**
   - `sync/clockMath.ts` со всеми функциями.
   - Установка vitest, конфиг.
   - `sync/clockMath.test.ts` — полное покрытие.
   - `npm test` — все зелёные.

5. **Frontend: класс `ClockSync` + хук**
   - `sync/ClockSync.ts`, `sync/useClockSync.ts`.
   - Интеграция в `App.tsx`: создать `clock`, подписаться на `WSClient`, передать в хук.

6. **Frontend: индикатор в UI**
   - В RoomPage показать `offset / rtt / count`.
   - Визуальная проверка в браузере при двух подключённых клиентах.

После шага 6 — обновить `NOTES.md` (сессия 3 — NTP-синхронизация) и зафиксировать всё одним финальным коммитом или объединить с шагом 6.

## 7. Критерии готовности

- [ ] При запущенном бэке и подключённом фронте в индикаторе через ~5 секунд появляются конкретные числа offset и rtt.

- [ ] `npm test` — все тесты `clockMath.test.ts` зелёные.
- [ ] При двух клиентах: разница `getServerTime()` между ними < 100 мс в стационарном режиме (грубая проверка корректности — можно вывести в консоль).

## 8. Согласованные решения

1. **`getRtt()` возвращает медиану RTT окна** (используется в логике для `uncertainty`). Для UI добавлен отдельный метод **`getLastRtt()`** — он реагирует на скачки и нагляднее в индикаторе.
2. **При реконнекте — жёсткий сброс окна** (`reset()`): пустое окно, warmup с нуля. Сеть после реконнекта может отличаться, старые измерения недостоверны.
3. **На `Error`-ответ от сервера на `TimeSyncRequest`** — `console.warn` и продолжаем. Протокольная ошибка на TimeSync — это баг, а не штатная ситуация.
