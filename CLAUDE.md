# Проект: Механизм синхронного воспроизведения мультимедиа

## Контекст
Дипломный проект студента 4 курса. Тема: «Проектирование и реализация механизма синхронного воспроизведения мультимедиа-контента в распределённом веб-приложении». СФУ, кафедра систем искусственного интеллекта, 2026 год.

**Суть проекта:** разработать открытый API синхронизации видеоплеера для нескольких пользователей в одной виртуальной комнате. Демонстрационный сайт — лишь обёртка, показывающая работу API. Основной вклад — сам механизм синхронизации, а не UI.

**Ключевая ценность — расширяемость:** механизм должен быть платформо-независимым. Поддержка нескольких видеохостингов (отечественных и зарубежных) реализуется через паттерн «адаптер плеера»: единый интерфейс синхронизации над разными iframe API. Это и есть «открытый API» из ТЗ.

## Целевые метрики (из ТЗ)
- Рассинхронизация между любыми двумя клиентами ≤ 400 мс (целевая ≤ 150 мс).
- Поддержка ≥ 30 одновременных участников в одной комнате.
- Восстановление синхронизации после обрыва — единицы секунд.
- Кросс-браузерность: Chromium, Firefox, Edge, Safari (последние стабильные).
- Серверная часть должна работать на типовом железе (4 ядра, 8 ГБ RAM).

- **SQLAlchemy 2.x** + **aiosqlite** — асинхронный доступ к БД.
- **SQLite** — хранилище сессий, логов событий, чата.

### Frontend
- **React 18+** через **Vite**.
- **TypeScript** — строгая типизация сообщений протокола.
- Никакого собственного видеоплеера — используются **встраиваемые плееры внешних видеохостингов** через iframe + postMessage API.
- Архитектура **адаптеров**: единый интерфейс `IPlayerAdapter` (`play()`, `pause()`, `seek(t)`, `setRate(r)`, `getCurrentTime()`, события `onPlay/onPause/onSeek/onTimeUpdate`), реализованный поверх API каждого хостинга. Добавление нового хостинга = новый класс-адаптер, без изменений в ядре синхронизации.
- Минимум сторонних UI-библиотек: цель — продемонстрировать механизм, а не дизайн.

## Архитектурные принципы

### Серверно-авторитетная модель
Сервер — единственный источник истины. Все клиенты подписаны на состояние сессии. Любое действие пользователя (Play/Pause/Seek/SetPlaybackRate) сначала отправляется на сервер, который рассылает команду всем участникам, включая инициатора. Локальное состояние плеера не меняется до подтверждения от сервера.

### Протокол сообщений (JSON по WebSocket)

Клиент → сервер:
- `Hello` — присоединение к сессии (session_id, nickname).
- `Play`, `Pause`, `Seek` (с позицией), `SetPlaybackRate` (со скоростью).
- `TimeSyncRequest` — клиентское время для NTP-подобной синхронизации.
- `ChatMessage` — текстовое сообщение.

Сервер → клиент:
- `Welcome` — текущее состояние сессии при подключении.
- `Play`, `Pause`, `Seek`, `SetPlaybackRate` — широковещательные команды от сервера всем клиентам с server_timestamp выполнения.
- `TimeSyncResponse` — серверное время для расчёта offset.
- `ParticipantJoined`, `ParticipantLeft` — события сессии.
- `ChatMessage`, `ChatModeration` — события чата.

Все сообщения включают поле `type` (строка) и `payload` (объект).

### NTP-подобная синхронизация часов
Каждый клиент периодически (каждые ~5 секунд) обменивается парой запрос-ответ с сервером для оценки:
- `offset` — смещение клиентских часов относительно серверных.
- `rtt` (round-trip time) — задержка туда-обратно.

Алгоритм: классический NTP — `offset = ((t1 - t0) + (t2 - t3)) / 2`, где t0/t3 — клиентское время до/после, t1/t2 — серверное время приёма/отправки. Берётся медиана из последних N измерений, выбросы по RTT отбрасываются.

### Применение команд с компенсацией задержки
Сервер при широковещании команды Play/Seek указывает `execute_at` — серверное время, в которое команда должна примениться (обычно `server_now + ~200 мс`). Клиент пересчитывает это в локальное время через свой offset и ставит таймер. Это даёт согласованное применение команды на всех клиентах независимо от их сетевой задержки.

### Архитектура адаптеров плееров

Сердце механизма синхронизации не знает, какой именно плеер используется. Оно работает с абстракцией `IPlayerAdapter`:

```typescript
interface IPlayerAdapter {
  // Управление
  play(): Promise<void>;
  pause(): Promise<void>;
  seek(seconds: number): Promise<void>;
  setPlaybackRate(rate: number): Promise<void>;

  // Состояние
  getCurrentTime(): Promise<number>;
  getDuration(): Promise<number>;
  isReady(): boolean;

  // События (для отслеживания пользовательских действий)
  on(event: 'play' | 'pause' | 'seek' | 'timeupdate' | 'ready', cb: Function): void;
  off(event: string, cb: Function): void;

  // Жизненный цикл
  destroy(): void;
}
```

#### Поддерживаемые плееры (приоритет — отечественные)

| Платформа | Embed URL | Способ управления |
|---|---|---|
| **RuTube** | `https://rutube.ru/play/embed/<video_id>` | `postMessage` (`player:play`, `player:pause`, `player:setCurrentTime`, события `player:changeState`, `player:currentTime`) |
| **VK Video** | `https://vk.com/video_ext.php?oid=...&id=...&js_api=1` | Скрипт `https://vk.com/js/api/videoplayer.js` + `VK.VideoPlayer(iframe)`, методы `play()`, `pause()`, `seek()`, события `started`, `paused`, `resumed`, `timeupdate` |
| YouTube (доп.) | `https://www.youtube.com/embed/<id>?enablejsapi=1` | YouTube IFrame API (`new YT.Player`, `playVideo`, `pauseVideo`, `seekTo`, `setPlaybackRate`) |
| Vimeo (доп.) | `https://player.vimeo.com/video/<id>` | Vimeo Player SDK (`new Vimeo.Player`, `play`, `pause`, `setCurrentTime`) |

#### Структура на фронте

```
frontend/src/players/
├── IPlayerAdapter.ts         # общий интерфейс + базовый класс
├── RutubeAdapter.ts          # реализация для RuTube
├── VKVideoAdapter.ts         # реализация для VK Video
├── YouTubeAdapter.ts         # доп.
├── VimeoAdapter.ts           # доп.
└── PlayerFactory.ts          # автоопределение хостинга по URL → нужный адаптер
```

`PlayerFactory.create(url)` парсит URL, определяет платформу и возвращает соответствующий адаптер. В UI пользователь просто вставляет ссылку на видео — система сама подбирает правильный адаптер.

#### Особенности реализации
- **Согласование сидинга:** разные плееры по-разному реагируют на `seek` во время паузы (одни остаются на паузе, другие начинают играть). Адаптер обязан нормализовать это поведение.
- **Точность `getCurrentTime`:** разные API возвращают позицию с разной частотой и точностью. Это закладывается в погрешность измерения рассинхрона.
- **Готовность плеера:** до события `ready` команды не отправляются в плеер, а буферизуются в адаптере.
- **Отслеживание пользовательских действий:** если пользователь нажал «пауза» в самом плеере (не через UI приложения), адаптер ловит это через событие и сообщает в синхронизатор, который шлёт команду на сервер.

## Правила для Claude Code

### Стиль работы
- Объяснять выбор решений простым языком, без излишней академической терминологии.
- Все числа — точные, без значительного округления. Если речь о метриках задержки или таймингах — указывать конкретные миллисекунды.
- При больших изменениях — сначала кратко описать план, потом писать код.
- Перед запуском shell-команд, которые могут что-то сломать (удаление, перезапись), — предупреждать.

### Код
- Python: типы (type hints) обязательно везде. Стиль — PEP 8, форматирование `ruff format`. Async везде, где идёт I/O.
- TypeScript: строгий режим (`"strict": true`). Никаких `any` без крайней необходимости.
- Имена осмысленные, на английском. Комментарии — на русском, если поясняют логику.
- Сообщения протокола: одна правда — Pydantic-схемы; TS-типы генерируются или поддерживаются вручную с проверкой.

### Тестирование
- Юнит-тесты для алгоритма синхронизации (вычисление offset, медиана, выбросы) — обязательно.
- Интеграционные тесты WebSocket-сценариев (подключение, рассылка команды, переподключение).
- Отдельный скрипт нагрузочного тестирования: эмуляция N клиентов, измерение реального рассинхрона.

### Что НЕ делать
- Не пытаться писать собственный видеоплеер — используются только встраиваемые плееры внешних хостингов через их iframe API.
- Не привязывать ядро синхронизации к конкретному плееру — всё через `IPlayerAdapter`.
- Не тащить тяжёлые зависимости (Redis, Kafka, Celery) — для масштаба 30 клиентов это лишнее.
- Не использовать WebRTC / P2P — выбрана централизованная модель.
- Не делать аутентификацию через OAuth и сложные системы — простой nickname + session token.
